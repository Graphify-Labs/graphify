## 1. Splat file formats: what exists, how each stores data, compression, SH, adoption, licensing

### Takeaway
There are four tiers in use today: (a) the de-facto lossless training/exchange layout (INRIA-style 3DGS `.ply`), (b) lossy web-delivery formats that are vendor-specified but open (`.spz` Niantic, `.sog`/Streamed SOG PlayCanvas, `.rad` Spark, `.ksplat`, `.splat`, compressed `.ply`), (c) one ratified standards-body container (GLB + `KHR_gaussian_splatting`, uncompressed), and (d) a new USD schema (`ParticleField3DGaussianSplat`). New or newly mature in 2026: SPZ v4 (ZSTD; commits 29 Apr-13 May 2026), Spark 2.x `.rad`, glTF extension ratified (3 Sep 2026), OpenUSD 26.03 schema (24 Feb 2026), X3D 4.1 draft `GaussianSplats` node implemented by X_ITE (31 May 2026); SOG v2 and Streamed SOG are the current PlayCanvas container/LOD specs (their first-release dates were not established).

### Cited Findings

**INRIA-style 3DGS `.ply` (de-facto source/archive format)**
- Header properties are `x y z`, `scale_0..2`, `rot_0..3`, `opacity`, `f_dc_0..2` (SH degree 0) and `f_rest_0..44` (45 higher-order SH coefficients = 9 + 15 + 21 for bands 1-3); data are float32, binary little-endian; PlayCanvas positions PLY as "Source & Interchange... Use for training, editing, archival storage... Lossless". — [PlayCanvas PLY doc (source)](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/ply.md), [PlayCanvas formats index (source)](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/index.md)
- PLY stores *pre-activation* values: scale in log space and opacity pre-sigmoid, whereas glTF stores linear scale and post-sigmoid opacity. — [PlayCanvas GLB doc (source)](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/glb.md)
- Licensing caveat: the INRIA/MPII reference *software* ("Gaussian-Splatting License") permits use "non-commercially, i.e., for research" and states the user cannot use/distribute the Software for commercial purposes. This is a software license, not a license over the PLY layout; I found no text asserting the PLY layout itself is encumbered. — [graphdeco-inria/gaussian-splatting LICENSE.md](https://github.com/graphdeco-inria/gaussian-splatting/blob/main/LICENSE.md)
- There is no standards-body spec for this PLY layout; Spark describes it as the "original 'gsplat' format" and supports plain x/y/z/r/g/b point clouds too. — [Spark loading-splats doc](https://github.com/sparkjsdev/spark/blob/main/docs/docs/loading-splats.md)

**`.splat` (antimatter15)**
- 32 bytes per splat in practice (Babylon's docs build a 32-byte row: float32 position x3, float32 size x3, RGBA uint8, quaternion uint8 x4) and Babylon describes it as "a JavaScript typed-array serialized version of .PLY data". — [Babylon.js Gaussian Splatting doc (source)](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/gaussianSplatting.md)
- No SH view-dependent color ("does not currently support view dependent shading effects with spherical harmonics... to reduce the file size"); 3dgsconverter lists `.splat` as "Legacy Web. RGB only (No SH)". Repo is MIT-licensed (Copyright 2023 Kevin Kwok) and its README now points to Spark as the "more advanced" renderer. — [antimatter15/splat README](https://github.com/antimatter15/splat/blob/main/README.md), [LICENSE](https://github.com/antimatter15/splat/blob/main/LICENSE), [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)

**`.ksplat` (mkkellogg GaussianSplats3D)**
- "My own custom `.ksplat` files, which are a trimmed-down and compressed" form; matches the viewer's internal layout so fastest to load; README admits "Custom `.ksplat` file format still needs work, especially around compression"; **the repo is "no longer in active development"** and recommends Spark. 3dgsconverter lists KSplat with max SH 2 and `compression_level` 0 (F32) / 1 (F16) / 2 (quantized). MIT license. — [GaussianSplats3D README](https://github.com/mkkellogg/GaussianSplats3D/blob/main/README.md), [LICENSE](https://github.com/mkkellogg/GaussianSplats3D/blob/main/LICENSE), [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)

**`.spz` (Niantic / Niantic Spatial; used by Scaniverse)**
- "Typically around 10x smaller" than the corresponding `.ply`; MIT license (Copyright 2024 Niantic Labs). — [nianticlabs/spz README](https://github.com/nianticlabs/spz/blob/main/README.md), [LICENSE](https://github.com/nianticlabs/spz/blob/main/LICENSE)
- **Version 4** (current): 32-byte plaintext header (magic `NGSP` = 0x5053474e, version, numPoints, shDegree 0-4, fractionalBits, flags, numStreams typically 6, tocByteOffset), optional extension records, a TOC, then N independently ZSTD-compressed attribute streams (positions, alphas, colors, scales, rotations, SH). Versions 1-3 are the legacy gzip single-stream format, "read-only". — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md)
- Attribute precision: positions 24-bit signed fixed-point per axis; scales 8-bit log-encoded; rotation (v3/v4) "smallest three" with 2-bit index + 10 bits per component (v2 used xyz at 8 bits each); alpha 8-bit; color 8-bit RGB; SH 8-bit signed with default quantization of 5 bits (SH1) and 4 bits (SH2+), configurable via `PackOptions` (`sh1Bits`, `shRestBits`, range 1-8). — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md)
- SH support: degrees 0-4 (0, 9, 24, 45 or 72 coefficients per Gaussian). Header flag 0x1 marks "trained with antialiasing". Vendor extensions as ILV records, e.g. `SPZ_ADOBE_coordinate_system` and `SPZ_ADOBE_safe_orbit_camera`. — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md)
- Default coordinate system RUB (OpenGL/three.js convention); README states PLY "typically" RDF, GLB "typically" LUF, Unity RUF; 16 named systems (8 standard + 8 rotated) with SH rotation via Wigner D-matrices when converting families. — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md)
- Timeline: parallel-GZip then ZSTD commits on 29 Apr 2026, V4 extension placement 30 Apr 2026, coordinate-system extension + rotated systems 13 May 2026, Python in-memory I/O 15 Jun 2026; library release tags are v1.0.0 (18 Apr), v1.1.0 (18 Apr), v2.0.0 (11 Jul), v2.1.0 (27 Oct; CLI tools + Python bindings), v3.0.0 (05 May; "ZSTD with parallel multi-stream encoding") — years not printed on the releases page (inferred 2025, 2025, 2025, 2025, 2026 from commit dates). Note the **library release number (v3.0.0) differs from the file-format version (4)**. — [spz commits](https://github.com/nianticlabs/spz/commits/main), [spz releases](https://github.com/nianticlabs/spz/releases)
- Ecosystem fragmentation on SPZ versions: PlayCanvas engine parser supports only v4 and rejects v1-3, ignores SH degree 4 and ignores the antialiased flag/vendor extensions; splat-transform reads v2-4 and writes v3 or v4 (default 4); X_ITE ships separate SPZ parser bundles for v4 and for v1-3; three.js PR author reported SPZ 4 files failing with a gzip error in an early build (issue #34187); the Khronos glTF SPZ-compression draft targets SPZ **v2** and "SPZ v4" is an unresolved question there. — [PlayCanvas SPZ doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/spz.md), [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md), [x_ite-spz-parser README](https://github.com/create3000/x_ite-spz-parser/blob/main/README.md), [three.js PR 33950](https://github.com/mrdoob/three.js/pull/33950), [glTF PR 2531](https://github.com/KhronosGroup/glTF/pull/2531)

**`.sog` / SOG v2 and Streamed SOG (PlayCanvas)**
- Spec name in PlayCanvas docs: **"SOG (Spatially Ordered Gaussians)"**; "typically 15-20x smaller than an equivalent PLY", lossy by design. Babylon's docs instead expand it as ".SOG/SOGS Self-Organizing Gaussian" and link the Fraunhofer HHI research repo, and 3dgsconverter distinguishes "SOG v2" from "SOGS v1 (legacy)" (v1 needs square textures). So **"SOG" (PlayCanvas v2 container) and "SOGS" (research-lineage v1) are not the same layout**; the expansion of the acronym differs by source. — [PlayCanvas SOG spec (source)](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/sog.md), [Babylon doc](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/gaussianSplatting.md), [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)
- Layout: `meta.json` (version 2) + lossless WebP images (`means_l/u`, `scales`, `quats`, `sh0`, optional `shN_centroids`/`shN_labels`); bundled form is a ZIP named `.sog`. Positions 16-bit per axis in a symmetric-log domain; quaternions 26-bit "smallest three" in (w,x,y,z) order; scales and SH0 via 256-entry codebooks; higher SH via a palette (up to 65,536 entries) of up to 3 bands, so max SH degree 3. Coordinate system: right-handed x right, y up, z back (RUB). Optional `model: "antialiased" | "2dgs"` tag. — [PlayCanvas SOG spec](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/sog.md)
- **Streamed SOG** (`lod-meta.json`, version 1): spatial tree of chunks at multiple LODs, each chunk an unbundled SOG, for "tens of millions of Gaussians". — [PlayCanvas Streamed SOG spec](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/streamed-sog.md)
- Tooling licence: splat-transform is MIT-style (Copyright 2011-2026 PlayCanvas Ltd.); SuperSplat editor repo is MIT. — [splat-transform LICENSE](https://github.com/playcanvas/splat-transform/blob/main/LICENSE), [SuperSplat repo](https://github.com/playcanvas/supersplat)
- PlayCanvas's own five-format list is PLY, SOG, Streamed SOG, GLB, SPZ, with workflow "Train and edit with PLY -> convert to SOG for production -> GLB when splats must flow through standard glTF pipelines". — [PlayCanvas formats index](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/index.md)

**`.compressed.ply` (SuperSplat / PlayCanvas)**
- "Chunk-based quantization stored in standard PLY container" (3dgsconverter's description); splat-transform reads and writes it (auto-detected on read); Spark loads the "compressed SuperSplat/gsplat variant". It is **not** in PlayCanvas's current five-format list (SOG supersedes it as the recommended compressed delivery format). — [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md), [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md), [Spark loading-splats](https://github.com/sparkjsdev/spark/blob/main/docs/docs/loading-splats.md)

**`.gsplat`**
- No distinct `.gsplat` file-format spec found. Spark uses "gsplat" only as a nickname for the original PLY layout. — [Spark loading-splats](https://github.com/sparkjsdev/spark/blob/main/docs/docs/loading-splats.md)

**LCC / LCC2 (XGrids)**
- splat-transform reads `.lcc` and `.lcc2` ("XGRIDS, octree") but cannot write them. I found no public spec text for LCC (xgrids.com not reachable). — [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md)

**Spark `.rad` (new in Spark 2.0; World Labs)**
- `.RAD` ("RADiance field") is "an extensible and configurable file format" storing a precomputed LoD splat tree, streamable with HTTP Range requests; chunked variant `*.rad` header + `*.radc` chunks; produced by the Rust `build-lod` tool (`tiny-lod` quick or `bhatt-lod` quality). Spark 2.x uses 16-byte `PackedSplats` or 32-byte `ExtSplats` (float32 centers) in memory. Spark is MIT and "Built by World Labs"; README example pins `spark@2.4.0`. — [Spark new-features-2.0](https://github.com/sparkjsdev/spark/blob/main/docs/docs/new-features-2.0.md), [Spark LoD getting started](https://github.com/sparkjsdev/spark/blob/main/docs/docs/lod-getting-started.md), [Spark README](https://github.com/sparkjsdev/spark/blob/main/README.md)
- Spark loads `.ply` (incl. compressed), `.spz`, `.sog`/`.zip` (SOGS), `.rad` by content sniffing and `.splat`/`.ksplat` by extension; `build-lod` accepts ply, spz, splat, ksplat, sog, zip. — [Spark loading-splats](https://github.com/sparkjsdev/spark/blob/main/docs/docs/loading-splats.md), [Spark LoD getting started](https://github.com/sparkjsdev/spark/blob/main/docs/docs/lod-getting-started.md)

**Other formats seen**
- `.spx` (Reall3d): "flexible, expandable... incorporates encoding methods from .splat, .spz and .sog and adds block compression", spec in the Reall3dViewer repo; supported by gsbox. — [gsbox README](https://github.com/gotoeasy/gsbox/blob/main/README.md)
- Triangle-splatting meshes stored in `.ply` are supported by Babylon.js. — [Babylon doc](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/gaussianSplatting.md)
- Parquet (columnar, "Data Analysis") and CSV are available as analysis outputs via 3dgsconverter / splat-transform. — [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md), [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md)
- NVIDIA "NuRec USDZ": custom USDZ container for Omniverse; "going to be deprecated and replaced by `ParticleField`". — [3DGRUT README](https://github.com/nv-tlabs/3dgrut/blob/main/README.md)
- GLB + `KHR_gaussian_splatting` and USD `ParticleField3DGaussianSplat`: see sections 2.

**Compact comparison (all values from the sources above)**

| Format | Compression | Max SH | Spec / owner | Adoption signals | Licence |
|---|---|---|---|---|---|
| INRIA `.ply` | none (float32) | 3 (f_rest_0..44) | de-facto, no body | everything; PlayCanvas "archival" | software: non-commercial research (INRIA) |
| `.splat` | ~none, 32 B/splat | 0 | antimatter15 | legacy web viewers | MIT |
| `.ksplat` | optional F16/quantized | 2 (per 3dgsconverter) | mkkellogg | GS3D (unmaintained), Spark reads | MIT |
| `.spz` v4 | ZSTD + quantization, ~10x | 4 | Niantic spz repo | Scaniverse, PlayCanvas, Spark, Babylon, three.js, Cesium, USD converter | MIT |
| `.sog` v2 | WebP+codebooks, 15-20x | 3 | PlayCanvas docs | PlayCanvas, Spark, Babylon, X_ITE plugin, gsbox | splat-transform MIT-style |
| Streamed SOG | per-chunk SOG + LOD tree | 3 | PlayCanvas docs | PlayCanvas, Babylon (experimental) | as above |
| `.compressed.ply` | chunk quantization | 3 | PlayCanvas/SuperSplat | Spark, splat-transform, gsbox (read) | - |
| `.rad` | LoD tree, chunked | per Spark | Spark | Spark only | MIT |
| GLB `KHR_gaussian_splatting` | none (float32 SH; optional normalized types for rot/scale/opacity) | 3 | Khronos (ratified) | see section 2 | Khronos IP framework |
| USD `ParticleField3DGaussianSplat` | none (USD arrays) | default 3 | OpenUSD / AOUSD IG | OpenUSD 26.03+, Isaac Sim 6.0 | OpenUSD licence |

### Inferences
- "Archive" and "delivery" needs are served by different members of this table; no single format is lossless, standards-ratified, SH-complete (including degree 4 and 2DGS/surfels) and streamable. The ratified glTF container is lossless but uncompressed (PlayCanvas: "Large (uncompressed, similar to PLY)").
- The acronym/layout ambiguity SOG vs SOGS and the SPZ v1-3 vs v4 split mean file extension alone does not identify a format version; a hub must sniff content/version rather than trust extensions.
- Spark `.rad` and PlayCanvas Streamed SOG are two incompatible LOD-streaming formats; Babylon already consumes the PlayCanvas one, so Streamed SOG currently has broader multi-engine support than `.rad`.

### Gaps
- No public LCC/LCC2 spec found; `.compressed.ply` byte-level spec not read (the PlayCanvas blog post was not reachable); `.ksplat` byte layout not read.
- KSplat/Spark `.rad` licences beyond repo MIT not checked for patent grants.
- XGrids' own LCC documentation could not be opened.

## 2. Standards: Khronos glTF, OpenUSD / AOUSD / NVIDIA, 3D Tiles / OGC, MPEG, Metaverse Standards Forum

### Takeaway
`KHR_gaussian_splatting` is **ratified** (registry commit of 3 Sep 2026; spec header reads "Complete, Ratified by the Khronos Group"); it is the base, uncompressed container. Its companion compression extensions (`..._compression_spz_2`, `..._lgsc`, `..._EGSC`, MPEG's `MPEG_GS`) are all still **open PRs, not ratified**. OpenUSD shipped a native `ParticleField` / `ParticleField3DGaussianSplat` schema in 26.03 (24 Feb 2026), and NVIDIA is moving from NuRec USDZ to it. 3D Tiles 1.1 carries splats as glTF content.

### Cited Findings

**KHR_gaussian_splatting - status and history**
- The README on `main` says: **Status: "Complete, Ratified by the Khronos Group"**; "Written against the glTF 2.0 spec"; copyright 2026, text CC-BY-4.0. — [KHR_gaussian_splatting README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)

The PR author of #2490 is weegeekps (Cesium). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [PR list](https://github.com/KhronosGroup/glTF/pulls?q=is%3Apr+gaussian)

**KHR_gaussian_splatting - what it specifies**
- Splats are glTF mesh primitives with `mode` POINTS (0); extension object has `kernel` (required; only `"ellipse"` defined), `colorSpace` (required; `srgb_rec709_display` or `lin_rec709_display`), `projection` (default `perspective`), `sortingMethod` (default `cameraDistance`). Material on the primitive MUST be ignored for splat rendering. Because splats are points, un-aware viewers can fall back to a sparse point cloud (optionally colored by `COLOR_0`). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)
- Attributes (README as of 22 Oct 2026): `POSITION` VEC3; `KHR_gaussian_splatting:ROTATION` VEC4 unit quaternion in glTF order, float32/snorm8/snorm16; `:SCALE` VEC3 **linear**, non-negative, float32/uint8/unorm8/uint16/unorm16; `:OPACITY` SCALAR **linear 0..1 (post-sigmoid)**, float32/unorm8/unorm16; `:SH_DEGREE_0_COEF_0` VEC3 required, `:SH_DEGREE_1_COEF_[0-2]`, `_2_COEF_[0-4]`, `_3_COEF_[0-6]` VEC3 optional; **all SH are float32 only**; no partial SH degrees; max degree 3 (up to 45 coefficients). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)
- Rendering rules: back-to-front alpha blending, splats are display-referred (scene lighting/exposure/tonemapping generally don't apply), SH rotated by node rotation, blending performed before any color gamut/transfer conversion. Extensions may add kernels, colour spaces, projections and sorting methods; compression extensions "SHOULD extend this base extension" and list themselves in `extensionsUsed`/`extensionsRequired`. — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)
- Coordinate convention: "recommended that the Gaussians are trained within the glTF coordinate system"; maintainers (Knyazev) clarified in issue #2613 (10 Jul 2026) that glTF's coordinate system is effectively required and source data in another system must be converted at export; an earlier explicit SPZ conversion paragraph was removed. Issue still open for wording. — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [issue 2613](https://github.com/KhronosGroup/glTF/issues/2613)
- Spec's own "Known Implementations": CesiumJS, Cesium Native, JSplat (javagl), 3dgs_ply2gltf (Huawei). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)

**Open issues against the ratified spec (as of 22 Oct 2026)**

## 3. X3D / Web3D Consortium / X_ITE and Gaussian splats

### Takeaway
There *is* concrete X3D activity: the **X3D 4.1 draft (ISO/IEC 19775-1 CD) defines a "Gaussian splats" component with a `GaussianSplats` node (abstract `X3DGaussianSplatsNode`)**, and **X_ITE implemented it** in v15.1 (31 May 2026) - experimental, component level 1 - along with PLY loading, SOG/SPZ via plugin parsers, and `KHR_gaussian_splatting` glTF import mapped onto that node. X_ITE's own docs list Castle Game Engine, FreeWRL, X3DOM and X3D-Edit as *not* supporting the node. X3D 4.1 itself is still a draft.

### Cited Findings

**X3D 4.1 draft node / component**
- The X3D Architecture 4.1 draft (ISO/IEC 19775-1:202x; URL tree is named `ISO-IEC19775-1v4.1-CD`, presumably "Committee Draft" - my reading of the URL) has a "43 Gaussian splats component"; it "integrates Gaussian splats extensions that provide support for direct real-time radiance-field rendering of volume data, without first converting into surface or line primitives", defines abstract `X3DGaussianSplatsNode`, and notes splats are based on radiance fields, not voxels, hence separate from the Volume rendering component. **[secondary: seen through a search-tool summary of the web3d.org page; page itself unreachable]** — [X3D 4.1 draft: Gaussian splats component](https://www.web3d.org/specifications/X3Dv4Draft/ISO-IEC19775-1v4.1-CD/Part01/components/gaussianSplats.html)
- The Java binding of X3D (X3DJSAIL) already exposes `org.web3d.x3d.jsail.GaussianSplats.GaussianSplats`. **[secondary]** — [X3DJSAIL javadoc](https://www.web3d.org/specifications/java/javadoc/org/web3d/x3d/jsail/GaussianSplats/GaussianSplats.html)
- Field-level definition (from X_ITE's node page, which cites the draft): hierarchy `X3DNode > X3DChildNode > X3DGaussianSplatsNode (X3DBoundedObject) > GaussianSplats`; "available from X3D version 4.1 or higher"; component `GaussianSplats`, support level 1; fields: `metadata`, `colorSpace` (SFString, default `"SRGB_REC709_DISPLAY"`, also `"LIN_REC709_DISPLAY"`), `positions` (MFVec3f), `orientations` (MFQuaternion, "usual glTF order (x,y,z,w)"), `scales` (MFVec3f, linear, >= 0), `opacities` (MFFloat, 0..1), sixteen `sphericalHarmonicsDegree{0..3}Coef{n}` MFVec3f fields (1+3+5+7 = SH degrees 0-3, "To use higher degrees... the lower degrees MUST be defined"), plus `pointerEvents`, `castShadow`, `visible`, `bboxDisplay`, `bboxSize`, `bboxCenter`. ### Inferences

- Because the node is a draft "CD" feature with no Castle/FreeWRL/X3DOM support, X3D interchange of splats should be treated as an *experimental spoke*; the robust path into X_ITE is glTF/GLB (`KHR_gaussian_splatting`) via Inline, with X3D 4.0 `PointSet` as a visual fallback.

## 4. Web renderers: three.js, Babylon.js, PlayCanvas, Spark, Cesium, A-Frame, model-viewer; WebGPU vs WebGL2, sorting, mobile limits

### Takeaway
All major web engines now render splats; the new facts for 2026 are **native three.js support (r186, 24 Sep 2026 - year inferred)**, **Babylon.js reading KHR_gaussian_splatting, SPZ, SOG and experimental Streamed SOG LOD**, and **Spark 2.x with LoD + `.rad` streaming**. Sorting is the central cost; mobile budgets are ~1-3 M splats without LOD.

### Cited Findings

**three.js**
- r186 (listed "24 Sep"; year inferred 2026) release notes: "Gaussian Splat renderer / loader using TSL for WebGPU/WebGL + glTF import" (#33950), raycasting (#34284), rename `GaussianSplatMesh` -> `GaussianSplat` (#34306), "View-dependent Gaussian Splatting via Spherical Harmonics" in `GLTFGaussianSplatLoaderExtension` (#34215), dedicated PLY loader (#34278). — [three.js r186 release](https://github.com/mrdoob/three.js/releases/tag/r186), [three.js releases](https://github.com/mrdoob/three.js/releases)
- PR #33950 (Ben Houston; merged 8 Aug 2026): TSL `NodeMaterial` "runs unmodified on both the WebGPU and WebGL backends"; initial loaders `.ply`, `.splat`, `.spz`, `.ksplat` plus opt-in glTF extension loader; **initial version stored only SH0** (view-dependent SH added in #34215); sort split into a `CountingSort` class; colour-space issue raised (alpha blending should occur in sRGB for sRGB-authored splats). — [PR 33950](https://github.com/mrdoob/three.js/pull/33950)
- Open problems: splats sorted per mesh only -> cross-mesh artifacts (#34256, milestone moved r186->r187 on 8 Sep 2026); GPU prefix-sum sort PR #34235; `drawRange` doesn't work; maintenance policy - core + SPLAT/KSPLAT/SPZ loaders stay in repo, SOG loader (#34252, bundled SOG v2 request, closed 16 Aug 2026) to live outside core. — [issue 34256](https://github.com/mrdoob/three.js/issues/34256), [issue 34252](https://github.com/mrdoob/three.js/issues/34252)
- mkkellogg/GaussianSplats3D: no longer in active development; CPU WASM-SIMD sort + partial GPU transform-feedback; recommends Spark; README lists splat-count limits depending on SH degree. — [GaussianSplats3D README](https://github.com/mkkellogg/GaussianSplats3D/blob/main/README.md)

**Spark (World Labs; THREE.js)**
- Targets WebGL2 ("98%+"), integrates with the three.js pipeline; loads PLY, SPZ, SPLAT, KSPLAT, SOG, RAD. 2.0 adds LoD splat tree with fixed per-frame budget N (default 500K-2.5M by device), shared LRU page table (default 16 M splats on GPU), HTTP-range streaming of `.rad`, "scenes with 100 M or 1 G+ splats can be rendered in real-time on mobile devices" (vendor claim). — [Spark README](https://github.com/sparkjsdev/spark/blob/main/README.md), [new-features-2.0](https://github.com/sparkjsdev/spark/blob/main/docs/docs/new-features-2.0.md)
- Vendor "splat budgets": Quest 3 <= 1 M, Android 1-2 M, iPhone 1-3 M, computer 1-5 M (10-20 M+ on some desktops); per-splat transform overhead becomes a bottleneck near ~1 M; many splats concentrated in a small screen area can bottleneck blending; advice: `antialias:false`, lower `maxStdDev` (e.g. sqrt(5) for VR). — [Spark performance doc](https://github.com/sparkjsdev/spark/blob/main/docs/docs/performance.md)

**Babylon.js**
- Native `GaussianSplattingMesh`; formats `.ply`, `.splat`, `.spz`, `.sog`/SOGS; `flipY` plugin option for SPZ; warns "Gaussian splatting files do not have a standard for handedness or orientation. No space-change operation will occur. Some scenes might appear upside down or mirrored." Shadows supported; `addPart` keeps a global sort order across assets; material debug plugins work on WebGL (GLSL) and WebGPU (WGSL); **experimental LOD streaming of PlayCanvas-style streamed SOG (`lod-meta.json`) on WebGL2 and WebGPU** with `memoryBudgetMb`. — [Babylon.js GS doc](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/gaussianSplatting.md)
- A glTF loader extension for `KHR_gaussian_splatting` exists in the repo (requires POINTS mode and POSITION; supports SH degrees by attribute presence; converts into Babylon's 32-byte row + SH textures). — [KHR_gaussian_splatting.pure.ts](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/loaders/src/glTF/2.0/Extensions/KHR_gaussian_splatting.pure.ts)
- Roadmap issue #16671 (created 26 May 2025; now closed, so partly stale - e.g. its unchecked "GS LOD" item is superseded by the experimental streamed-SOG LOD in the docs) shows checked: SOG evaluation, WASM SPZ loader, ortho, shadows, GPU picking; unchecked: 4th-order SH (PR #18459), GS LOD, "optional sorting using Compute Shader". — [Babylon issue 16671](https://github.com/BabylonJS/Babylon.js/issues/16671)

**PlayCanvas**
- Engine + SuperSplat editor (MIT). Engine: GLB containers (only `ellipse` kernel; `sortingMethod`/`projection` ignored), SPZ via a parser script (v4 only; SH up to 3 bands; ~20 bytes/splat plus SH kept quantized in GPU memory), SOG, Streamed SOG, PLY. All GSplat components share one **global sort** via a work buffer. — [PlayCanvas GLB doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/glb.md), [SPZ doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/spz.md), [rendering architecture](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/rendering-architecture/index.md)

**CesiumJS, X_ITE** - see sections 2 and 3 (CesiumJS WebGL, 3D Tiles; X_ITE WebGL, glTF/PLY/SOG/SPZ).

**A-Frame, model-viewer**
- Searches of `aframevr/aframe` and `google/model-viewer` GitHub issues for Gaussian-splat support returned 0 results. No evidence found of first-party splat support in either.

### Inferences
- WebGPU is not required: the three.js TSL path, Babylon.js and PlayCanvas run on WebGL2 as well; WebGPU mostly helps GPU-side sorting (prefix-sum/compute) and memory handling. Spark chooses WebGL2-only for reach, and sorts remain the limiting step either way.
- Global-sort correctness across multiple splat objects is the main interoperability trap for a Blender-style multi-asset scene: PlayCanvas (global), Babylon (`addPart`), Spark (multi-object LoD) handle it; three.js core does not yet (r187 target).
- Mobile reality: with no LOD, plan for ~1-2 M splats on phones (Spark's own budgets); exceeding that requires LOD formats (Streamed SOG, `.rad`, 3D Tiles).

### Gaps
- No independent benchmarks (frame time vs splat count, WebGPU vs WebGL2) found; only vendor guidance.
- A-Frame community components and model-viewer roadmaps not located (first-party: no evidence).
- PlayCanvas engine's WebGPU compute-sort details not read.
- Exact three.js release year (r186) not printed; inferred from PR dates.

## 5. Format-conversion tooling; lossy/lossless considerations; coordinate-system pitfalls

### Takeaway
Conversion is well-served by `splat-transform` (broadest), `gsbox`, `3dgsconverter`, Niantic `spz` tools, and Huawei's `3dgs_ply2gltf`; but **splat-transform writes GLB and cannot read it**, only SPZ/SOG/etc. are lossy, and the biggest silent-failure sources are coordinate frames, quaternion order, activation functions (log scale / logit opacity vs linear / sigmoid), SH layout/degree, and colour space.

### Cited Findings

**Tools**
- **splat-transform (PlayCanvas)**: reads PLY, compressed PLY, SOG, `meta.json`, `lod-meta.json`, SPZ (v2-4), LCC, LCC2, KSPLAT, SPLAT; writes PLY, compressed PLY, SOG, Streamed SOG, SPZ (v3 or v4, default 4), **GLB** (`KHR_gaussian_splatting`), CSV, HTML viewer, LOD, voxel, WebP images; **GLB is marked input "no"**. Preserves 2DGS / antialiased tags where the output can (SOG, SPZ antialiased bit; SPZ cannot represent 2DGS and warns; other outputs drop the tag silently). Also transforms, filters, LOD generation. — [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md)
- **gsbox**: converts among `.ply`, `.splat`, `.spx`, `.spz`, `.sog`, `.glb` (only GLB with `KHR_gaussian_splatting`; write since v4.7.0, read since v4.7.1), reads `.compressed.ply` and `.ksplat`, applies rotation/scale/translation, generates `lod-meta.json`. — [gsbox README](https://github.com/gotoeasy/gsbox/blob/main/README.md)
- **3dgsconverter** (francescofugazzi): N-to-N among 3DGS PLY, CloudCompare-style PLY (forces RGB), compressed PLY, `.splat` (SH 0), KSplat, SPZ v3/v4, SOG v2 / SOGS v1, Parquet; GPU (Taichi) k-means for SOG/KSplat; SH4 only via opt-in `--preserve_sh4` (experimental). — [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)
- **Niantic spz**: C++ lib + Python bindings (nanobind) + WASM/TS; CLI tools for PLY<->SPZ (added v2.1.0); browser converter at nianticlabs.github.io/spz for files up to ~2 GB; `PackOptions.from` / `UnpackOptions` take a coordinate system for conversion. — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md), [spz releases](https://github.com/nianticlabs/spz/releases)
- **Khronos-side**: `3dgs_ply2gltf` (Huawei; PLY -> glTF+bin; `--convert` applies a -90 degree rotation about X to go from right-handed Z-up to Y-up; `--dump` writes the buffer back to PLY for verification) and `JSplat` (javagl) are the two reference converters/viewers named in the spec. No official Khronos conversion tool beyond these found. — [3dgs_ply2gltf README](https://github.com/NorbertNopper-Huawei/3dgs_ply2gltf/blob/main/README.md), [KHR README (Known Implementations)](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)
- **NVIDIA 3DGRUT**: PLY <-> USD ParticleField <-> NuRec USDZ transcoding; also a PLY->USDZ path. OpenUSD itself ships an SPZ->USD converter (26.05). — [3DGRUT README](https://github.com/nv-tlabs/3dgrut/blob/main/README.md), [OpenUSD CHANGELOG](https://github.com/PixarAnimationStudios/OpenUSD/blob/release/CHANGELOG.md)
- Browser-based: SuperSplat Convert (frontend to splat-transform). — [splat-transform README](https://github.com/playcanvas/splat-transform/blob/main/README.md)

**Lossy vs lossless facts**
- Lossless (up to float rounding/activation): PLY <-> GLB base extension (float32 SH) as long as SH degree <= 3 and kernel is ellipse. PlayCanvas labels GLB "Lossless" and SPZ/SOG "Lossy". — [PlayCanvas formats index](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/index.md)
- Lossy: SPZ (24-bit fixed point positions, 8-bit log scales, 10-bit quaternion components, 8-bit alpha/colour, 4-5 bit SH by default), SOG (16-bit log positions, 26-bit quats, 256-entry codebooks, SH palette clustering), `.splat` (8-bit colour, **drops all SH**), KSplat level 2 (quantized, SH <= 2 per 3dgsconverter), compressed.ply (chunk quantization). — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md), [SOG spec](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/sog.md), [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)
- SH-capacity mismatches: SPZ v4 up to degree 4 (PlayCanvas ignores the 4th band); glTF/SOG up to degree 3; `.splat` degree 0; 3dgsconverter caps default at 3 unless `--preserve_sh4`. — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md), [PlayCanvas SPZ doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/spz.md), [3dgsconverter README](https://github.com/francescofugazzi/3dgsconverter/blob/main/README.md)
- A glTF-side reviewer (weegeekps, Oct 2026) cites EntropyGS research on Laplacian SH distributions and "visible artifacts from uniform quantization in SPZ". — [issue 2674](https://github.com/KhronosGroup/glTF/issues/2674)

**Coordinate / convention pitfalls**
- PLY (typical 3DGS training output) ~ RDF; SPZ default RUB; glTF ~ LUF (+Y up, asset faces +Z); Unity RUF; SOG = right-handed x right, y up, z back; PlayCanvas: PLY needs a flip rotation on load, GLB/SPZ do not; Spark example re-orients OpenCV->OpenGL with quaternion (1,0,0,0) (180 degrees about X); Babylon performs no handedness conversion (`flipY` only for SPZ); ply2gltf's `--convert` is -90 degrees about X. — [spz README](https://github.com/nianticlabs/spz/blob/main/README.md), [SOG spec](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/sog.md), [PlayCanvas GLB doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/glb.md), [Spark loading-splats](https://github.com/sparkjsdev/spark/blob/main/docs/docs/loading-splats.md), [Babylon doc](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/gaussianSplatting.md), [ply2gltf README](https://github.com/NorbertNopper-Huawei/3dgs_ply2gltf/blob/main/README.md)
- Quaternion order: SOG stores (w,x,y,z); glTF `ROTATION` and X_ITE `orientations` are (x,y,z,w); the SPZ-in-glTF draft debates SPZ's LUF vs RUB and 3D Tiles 1.1's `UNSPECIFIED`. — [SOG spec](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/sog.md), [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [PR 2531](https://github.com/KhronosGroup/glTF/pull/2531)
- Rotating a splat requires rotating SH coefficients (glTF: "SH coefficients are rotated by the node's rotation"; SPZ: Wigner D-matrix when switching coordinate families). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [spz README](https://github.com/nianticlabs/spz/blob/main/README.md)
- Colour space: glTF splats are display-referred and carry an explicit `colorSpace` (`srgb_rec709_display` default or `lin_rec709_display`); SH0 colour reconstruction uses constant 0.2820947917738781 with a +0.5 bias. SPZ's `colorScale` interplay with that 0.282/0.5 pair is an open question in the SPZ-for-glTF draft. — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [PR 2531](https://github.com/KhronosGroup/glTF/pull/2531)
- Non-uniform scale: Spark ignores non-uniform scaling unless `covSplats` is enabled. — [Spark new-features-2.0](https://github.com/sparkjsdev/spark/blob/main/docs/docs/new-features-2.0.md)

**Blender**
- Searches of `KhronosGroup/glTF-Blender-IO` issues for Gaussian-splat / KHR_gaussian_splatting import-export returned no relevant results; GitHub repo-search for Blender splat add-ons failed (502) on every attempt. **No evidence found** of first-party Blender (or Blender glTF IO) support for `KHR_gaussian_splatting` as of this research.

### Inferences
- A safe conversion chain for a Blender-centred hub is: training PLY (source of truth) -> normalized in-hub attribute set that already uses glTF conventions (linear scale, sigmoid opacity, xyzw quaternion, Y-up, per-coefficient SH VEC3, explicit colour-space tag) -> exporters per spoke (GLB for standards spokes, splat-transform for SOG/SPZ, USD for NVIDIA). Doing the activation/axis/quaternion normalization exactly once, at ingest, avoids compounding errors.
- Because splat-transform cannot read GLB, a round trip GLB -> SOG/SPZ via splat-transform is not possible directly; go via PLY (splat-transform can't produce PLY from GLB either) - hence the hub must own a GLB reader (gsbox reads GLB from v4.7.1; X_ITE/Babylon/three.js have loaders in-browser).
- The SH-per-coefficient layout differs between PLY (`f_rest_*` flattened) and glTF/SPZ (`VEC3` per coefficient, colour channel innermost) - I did not find a source that spells out the PLY `f_rest` channel ordering, so verify with a round-trip test (e.g. ply2gltf `--dump`) before trusting any converter.

### Gaps
- Exact PLY `f_rest_*` channel ordering vs SPZ/glTF ordering not documented in sources read.
- No quantitative round-trip error numbers (PSNR/LPIPS) for SPZ vs SOG vs glTF found in sources.
- Khronos "conversion tools" beyond ply2gltf/JSplat: none found; Cesium ion / 3d-tiles-tools splat tiling tooling not verified.
- Blender add-on landscape (KIRI 3DGS Render etc.) not verified because repo search failed.

## 6. Recommendation: canonical archive vs runtime delivery vs DCC exchange (late 2026)

### Takeaway
Use **raw training PLY as the canonical archive** (with a sidecar recording frame/colour-space/activation) and **GLB + `KHR_gaussian_splatting` as the canonical DCC/interchange format** (the only ratified, vendor-neutral, multi-engine container); use **SOG v2 / Streamed SOG (or SPZ v4 when Niantic/Scaniverse-originated) for runtime web delivery**, USD `ParticleField` as the NVIDIA/Omniverse spoke, and X3D 4.1 `GaussianSplats` only as an experimental X_ITE spoke.

### Cited Findings
- PlayCanvas guidance: PLY "Use for: Training, editing, archival storage / Lossless"; SOG "Use for: Web apps, real-time rendering, CDN delivery"; GLB "Use for: Interoperability, standard glTF tooling and pipelines / Large (uncompressed)"; SPZ "assets from the Niantic/Scaniverse ecosystem". — [PlayCanvas formats index](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/index.md)
- Standards state: `KHR_gaussian_splatting` ratified (3 Sep 2026); all compression companions unratified; USD ParticleField shipped in OpenUSD 26.03; NVIDIA prefers ParticleField over NuRec USDZ; X3D 4.1 `GaussianSplats` is a draft implemented by X_ITE. — see sections 2 and 3 for sources.
- Implementation breadth of the glTF extension (reading or writing): CesiumJS/Cesium Native, JSplat, ply2gltf (spec list); PlayCanvas (write via splat-transform, GLB load), Babylon.js (loader), three.js (opt-in loader), X_ITE (native), gsbox (read/write). — [KHR README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md), [PlayCanvas GLB doc](https://github.com/playcanvas/developer.playcanvas.com/blob/main/docs/user-manual/gaussian-splatting/formats/glb.md), [Babylon loader](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/loaders/src/glTF/2.0/Extensions/KHR_gaussian_splatting.pure.ts), [three.js PR 33950](https://github.com/mrdoob/three.js/pull/33950), [X_ITE Features](https://github.com/create3000/x_ite/blob/main/docs/_posts/features.md), [gsbox README](https://github.com/gotoeasy/gsbox/blob/main/README.md)

### Inferences
Decision table (my reasoning from the findings above):

| Role | Pick | Why | Watch-outs |
|---|---|---|---|
| Canonical archive (long-term, lossless, richest) | Original training PLY (+ sidecar JSON: source tool, coordinate frame, colour space, activation conventions, antialiased/2DGS flag, SH degree) | Lossless, supports SH4/2DGS tags and trainer-specific extras, readable by every tool; PlayCanvas itself recommends PLY for archival | PLY layout has no governing standard; INRIA software licence is non-commercial research (check your training tool's licence); huge files |
| Standards-based archive alternative | GLB + `KHR_gaussian_splatting` (float32 SH <= 3, ellipse kernel) | Ratified, Khronos IP framework, explicit colour space and activation, can carry meshes in the same file | Loses SH4 / surfel / 2DGS; spec edited 13 Oct 2026 (pin commit); no quantization story yet (#2674) |
| DCC exchange (Blender hub <-> spokes) | **GLB + KHR_gaussian_splatting** with glTF conventions (Y-up, xyzw, linear scale, sigmoid opacity) | Only ratified multi-vendor option; direct readers in Cesium, X_ITE, Babylon, PlayCanvas, three.js; one-to-one with X3D `GaussianSplats` and close to USD `ParticleField` | Blender has no first-party support (no evidence found) -> custom importer/exporter; mixed mesh+splat scenes are poorly supported by renderers (#2562) |
| Runtime web delivery (single scene) | SOG v2 bundled (`.sog`), generated with splat-transform | 15-20x smaller than PLY, readable by PlayCanvas, Spark, Babylon, X_ITE (plugin), gsbox | Lossy; max SH 3; acronym ambiguity with SOGS v1; not a standards-body spec |
| Runtime web delivery (very large scenes) | Streamed SOG (`lod-meta.json`) -> PlayCanvas/Babylon; `.rad` only if Spark-only; 3D Tiles 1.1 + KHR_gaussian_splatting(+spz_2) for geospatial/Cesium | LOD + streaming; mobile-friendly | Two incompatible LOD formats; spz_2 compression unratified |
| Mobile/phone-originated assets | SPZ v4 | Native to Scaniverse/Niantic; ~10x; ZSTD | v1-3 vs v4 fragmentation; some engines accept only v4 |
| NVIDIA / Isaac Sim / Omniverse spoke | USD `ParticleField3DGaussianSplat` | Standard USD in OpenUSD >= 26.03; NuRec USDZ being deprecated | Not evidenced as AOUSD-ratified spec; Blender USD IO support unverified |
| X3D spoke | glTF/GLB via Inline (X_ITE) first; X3D 4.1 `GaussianSplats` node second; X3D 4.0 coloured `PointSet` as visual fallback | X_ITE is the only implementing browser; node mirrors glTF extension | 4.1 is a draft "CD"; only X_ITE; not for big scenes inline |

Additional reasoning: do not use `.splat`/`.ksplat` as hub formats (no/limited SH, one maintainer-unsupported); do not treat SPZ or SOG as archive formats (lossy); treat any "canonical" choice as dependent on pinning versions (SPZ v4, SOG meta v2, KHR README commit after 13 Oct 2026).

### Gaps
- Whether Blender (5.x) or its glTF exporter will gain `KHR_gaussian_splatting` support: no evidence found.
- Whether `KHR_gaussian_splatting_compression_spz_2` will be ratified, and whether it will target SPZ v2 or v4: unresolved in PR #2531.
- Independent quality/size benchmarks for SPZ vs SOG vs glTF would sharpen the delivery choice; none found.
- Licensing review of trainers (INRIA vs permissively-licensed alternatives such as 3DGRUT/gsplat) not done; only the INRIA licence text was read.
